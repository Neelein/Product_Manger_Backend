# Fix session cookie Secure flag for HTTP (E2E auth failures)

## What
- Added `src/api/session_cookie.go` with `isHTTPS`, `sessionCookie`, and `clearSessionCookie` helpers.
- Replaced the three hardcoded `Secure: true` cookie literals in `member_handler.go` (login, logout) and `middleware.go` (session refresh) with these helpers. `Secure` is now set only when the request is over TLS or carries `X-Forwarded-Proto: https`.
- Added unit tests (`src/api/session_cookie_test.go`) for the cookie Secure flag across plain-HTTP, TLS, and forwarded-proto cases, plus integration assertions in `src/test/api/member_handler_test.go`.

## Why
The `session_key` cookie was set with `Secure: true`. The app runs over plain HTTP in development and E2E (`http://localhost:5173` -> Vite proxy -> backend `http://localhost:8090`, no TLS; see `main.go`). Browsers reject `Secure` cookies over non-HTTPS origins, so the session cookie was never stored. Login appeared to work (the frontend keeps the member in React state) but any full page reload lost the session and redirected to `/login`, causing the whole Playwright E2E suite (auth, product, inventory, announcement, calendar, chat) to time out.

Over HTTPS/TLS (or behind a proxy sending `X-Forwarded-Proto: https`) the cookie is still marked `Secure`, preserving production security.

## Key decisions
- `Secure` is derived from the request scheme (`r.TLS != nil || X-Forwarded-Proto == https`) rather than a new env config — no new configuration surface.
- Logout clearing cookie also uses the scheme refactor to keep behavior symmetric.
