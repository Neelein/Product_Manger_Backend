# Database test isolation (`src/test/database`)

## What
Changed `src/test/database/product_repo_test.go` to use its own dedicated Postgres database `productdb_database_test` instead of the shared default `productdb_test`.

## Why
`src/test/api/handler_test.go` and `src/test/database/product_repo_test.go` each had a `TestMain` that defaulted to the same `productdb_test` database and ran identical `dropTables` + `runMigration`. When `go test ./src/test/...` runs packages in parallel, they raced on the same tables (deadlocks, missing relations, FK violations). Running each package individually passed, masking the bug.

## How
- Default fallback URL (when `TEST_DATABASE_URL` is unset) now points at `productdb_database_test`. An explicit `TEST_DATABASE_URL` override is still honored.
- Added `ensureTestDatabase(ctx, u *url.URL)`, called from `TestMain`, which connects to the admin `postgres` database, checks `pg_database` for the target db, creates it if missing (name quoted via `pgx.Identifier{...}.Sanitize()`), and panics on error.
- Added `net/url`, `strings`, and `github.com/jackc/pgx/v5` imports (for `pgx.Identifier`); `pgxpool` was already imported.

## Changes
- `src/test/database/product_repo_test.go`

## Verification
- `gofmt -l` clean, `go vet -tags=integration` clean, `go build ./...` passes.
- `go test -tags=integration -count=1 ./src/test/...` passes all packages together (`api`, `database`, `domain`), confirming isolation.
